# LINE グループ タスク管理ボット

グループ LINE の会話を読み、やるべきタスクを抽出して台帳化し、実行まで持っていくボットです。

```
グループLINE ──webhook──▶ Cloud Run ──▶ messages シート（会話ログ）
                                              │
                              Cloud Scheduler（10分おき）
                                              ▼
                                   Claude が会話を読んで理解
                                              │
                              ┌───────────────┴───────────────┐
                              ▼                               ▼
                     tasks シート（台帳）            実行アクションの立案
                              │                               │
                    リマインド／日次サマリー      ┌────────────┴────────────┐
                              │                  ▼                         ▼
                              └──────────▶ 低リスク: 自動実行      高リスク: LINEで承認
                                            （カレンダー登録等）    （メール送信等）
```

## できること

| 機能 | 内容 |
|---|---|
| 会話の理解 | グループの発言から「実際に誰かがやること」を抽出。雑談・感想・完了報告は除外する |
| タスク台帳 | Google スプレッドシートに担当・期限・優先度つきで蓄積。人が直接見て直せる |
| 状態の追随 | 「終わりました」等の発言を検出して既存タスクを完了に更新 |
| リマインド | 期限が近い／過ぎたタスクをグループへ通知（同一タスクは 1 日 1 回まで） |
| 日次サマリー | 朝いちで未完了タスク一覧を投稿 |
| 実行 | カレンダー登録、Gmail 下書き・送信、LINE 通知。リスクに応じて自動実行か承認制かが決まる |
| チャット操作 | 「タスク」「完了 3f2a」など日本語のコマンドと、一覧のボタン操作 |

## 設計上の重要な判断

**1. webhook は溜めるだけ。理解はジョブでまとめて行う。**
LINE の webhook は数秒で応答する必要があり、Cloud Run はリクエスト外で CPU が絞られます。
発言 1 件ごとに LLM を呼ぶのはコスト面でも文脈面でも不利なので、webhook は
`messages` シートに積むだけにして、Cloud Scheduler から数分おきに走る解析ジョブが
まとめて読みます。文脈がまとまって渡るぶん、抽出精度も上がります。

**2. LLM に実行権限を直結させない。**
Claude が出すのは「実行案」までで、実際の副作用は `src/actions/executor.ts` を必ず通ります。
リスク判定（`AUTO_EXECUTE_MAX_RISK`）を超えるものは `actions` シートに承認待ちで積まれ、
LINE 上のボタンを人が押すまで実行されません。既定ではメール送信は必ず承認制です。

**3. 重複防止はプロンプトとコードの二重で行う。**
同じ依頼が言い換えで再登場すると LLM は別タスクとして出しがちです。
既存タスクを毎回プロンプトへ渡したうえで、根拠メッセージ ID の重なりと
タイトルの類似度でコード側でも弾いています（`filterNewTasks`）。

**4. 保存先はスプレッドシート。**
既存の業務フローと同じ運用感で、人が直接開いて直せることを優先しました。
件数が数千行を超えて遅くなったら `src/store/` の repo 層だけを Firestore などに差し替えます。

## セットアップ

[docs/setup.md](docs/setup.md) に手順をまとめています。おおまかには次の 4 つです。

1. LINE 公式アカウント（Messaging API チャネル）を作り、グループトーク参加を許可する
2. Google Cloud プロジェクトでサービスアカウントを作り、スプレッドシートを共有する
3. Secret Manager にシークレットを登録して Cloud Run へデプロイする
4. Cloud Scheduler のジョブを作る

## ローカル開発

```bash
npm install
cp .env.example .env     # 値を埋める
npm run dev              # http://localhost:8080
npm test                 # ネットワークに触れないテスト
npm run typecheck
```

webhook をローカルで受けるには ngrok などでトンネルを張り、
LINE Developers コンソールの Webhook URL に `https://<tunnel>/line/webhook` を設定します。

## グループ内のコマンド

| コマンド | 動作 |
|---|---|
| `タスク` | 未完了タスクの一覧（ボタンつき） |
| `今日` | 24 時間以内が期限のタスク |
| `解析` | 直近の会話をいますぐ解析する |
| `完了 <ID>` | タスクを完了にする |
| `追加 <内容>` | タスクを手動で追加 |
| `実行案 <ID>` | そのタスクに対する実行案を立てる |
| `ヘルプ` | 使い方 |

コマンド語は完全一致（または「語 + 引数」）でのみ反応します。
「タスクが多いですね」のような普通の発言は会話として扱われます。

## エンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/healthz` | ヘルスチェック |
| POST | `/line/webhook` | LINE からの webhook（署名検証あり） |
| POST | `/jobs/analyze` | 会話解析（Cloud Scheduler） |
| POST | `/jobs/reminders` | 期限リマインド（Cloud Scheduler） |
| POST | `/jobs/digest` | 日次サマリー（Cloud Scheduler） |
| POST | `/admin/bootstrap` | シートの初期化（初回のみ） |

`/jobs/*` と `/admin/*` は `x-job-secret` ヘッダで保護されています。

## 運用コストの目安

既定のスケジュール（平日 8〜20 時に 10 分おき）だと 1 グループあたり最大 78 回／日の起動です。
ただし未処理メッセージが無い回は API を呼ばずに終わるので、実際の呼び出し回数は会話量次第で
これよりかなり少なくなります。

仮に全 78 回で API を呼び、1 回あたり入力 3,000 トークン（既存タスク＋文脈＋対象メッセージ）、
出力 500 トークンとした場合の上限は、`claude-opus-5`（$5 / $25 per MTok）で 1 グループ 1 日あたり
およそ **$2.1** です。抑えたい場合は次のいずれかを調整します。

- `ANTHROPIC_MODEL=claude-sonnet-5` に変更する（$3 / $15 per MTok。上限で約 $1.3／日）
- Cloud Scheduler の間隔を 10 分から 30 分へ広げる
- `ANALYZE_MIN_MESSAGES` を上げて、発言が溜まるまで解析しないようにする

実際の消費量は会話量に強く依存します。まず 1 グループで 1 週間動かして
Cloud Logging の `inputTokens` / `outputTokens` を見てから調整することをおすすめします。

## 注意点

- **プライバシー**: グループの発言内容が Anthropic API とスプレッドシートに渡ります。導入前にメンバーへ周知してください。
- **Gmail の実行**: サービスアカウント単体では Gmail を操作できません。ドメイン全体の委任の設定が必要です（[docs/setup.md](docs/setup.md)）。設定しない場合、Gmail アクションは実行時にエラーを返し、他の機能には影響しません。
- **メッセージ ログの保持**: `messages` シートは無制限に伸びます。運用に合わせて古い行を定期削除してください。
